# Chatbot V3 Phase 1.1 Generic Events And TurnPlan Design

Date: 2026-04-27

## Status

Approved design direction pending final user review.

This document specifies the Phase 1.1 control-plane refactor for chatbot-v3:

- Replace overly specific semantic supervisor event names with generic semantic events plus `target` and `modifier`.
- Replace the single `nextAction` reducer output with a `TurnPlan` that supports answer-then-advance behavior.
- Keep deterministic frontend/system events stable.
- Keep the current physical agents initially, while introducing clearer conceptual agent roles.
- Use a code-defined skill pack registry for Phase 1.1.

## Problem

The current semantic event model mixes several dimensions in one enum:

- User intent: `USER_WANTS_DOCTOR_OR_HOSPITAL_MATCHING`
- Content type: `USER_PROVIDED_MEDICAL_FACTS`
- Question category: `USER_ASKED_FAQ`
- User stance: `USER_REJECTED_OR_HESITATED`
- Provided business data: `USER_PROVIDED_CONTACT_INFO`

This works for the first set of test cases, but it will not scale. New real-world turns would pressure the system to add event names such as:

- `USER_WANTS_NEW_RECOMMENDATION`
- `USER_REJECTED_DOCUMENT_UPLOAD`
- `USER_REJECTED_CONTACT_INFO`
- `USER_WANTS_CHEAPER_HOSPITAL`
- `USER_WANTS_CITY_SPECIFIC_HOSPITAL`

Those should not become event types. They are combinations of:

- What kind of turn this is.
- What object the user is talking about.
- What stance or operation the user is expressing.

The current single `nextAction` output also underspecifies normal customer-service behavior. Many turns need two parts:

1. Answer, acknowledge, redirect, or set a safety boundary.
2. Then invite the next workflow step.

Example:

```text
User: 大概多少钱？

Reply should answer pricing uncertainty, then invite records upload.
```

A single `ANSWER_FAQ` action cannot fully express that control-plane intent.

## Goals

1. Shrink semantic event types to a stable generic taxonomy.
2. Preserve deterministic events for structured frontend/system actions.
3. Add `target` and `modifier` as first-class supervisor outputs.
4. Make reducer output a `TurnPlan`, not only one `nextAction`.
5. Support answer-then-advance responses without letting agents decide workflow truth.
6. Keep safety and out-of-scope as high-priority semantic events.
7. Introduce skill packs through a deterministic code registry.
8. Keep Phase 1.1 implementable without building a skill CMS, DB-backed editor, or new physical agent fleet.

## Non-Goals

- Do not build a database-backed skill management system in Phase 1.1.
- Do not require UI button rendering for choices.
- Do not introduce a separate `REVISIT` primary action.
- Do not add `ASK_CHOICE`; choice-style prompts are covered by `ASK_QUALIFYING_QUESTION`.
- Do not add `RETURN_TO_MAIN_FLOW`; concrete follow-up targets express the next step.
- Do not physically rename all existing agents immediately.
- Do not let the LLM decide stages, persistence, agents, tools, or write patches.

## Event Taxonomy

### Deterministic Events

These remain structured/system-driven and are not generated by the semantic LLM:

```ts
type DeterministicEventType =
  | 'TRIAGE_SUBMITTED'
  | 'TRIAGE_SKIPPED'
  | 'RECOMMENDATION_SELECTED'
  | 'RECOMMENDATION_SKIPPED'
  | 'DOCUMENTS_UPLOADED';
```

`USER_REQUESTED_HUMAN` can be deterministic when detected by runtime phrases or structured action, but it also exists in the semantic set for cases where the user naturally asks for a person.

### Semantic Events

```ts
type SemanticEventType =
  | 'USER_EXPRESSED_NEED'
  | 'USER_ASKED_QUESTION'
  | 'USER_PROVIDED_INFORMATION'
  | 'USER_RESPONDED_TO_REQUEST'
  | 'USER_REQUESTED_HUMAN'
  | 'USER_ASKED_RISKY_MEDICAL_ADVICE'
  | 'USER_ASKED_OUT_OF_SCOPE_OR_RESTRICTED_SERVICE'
  | 'USER_MESSAGE_UNCLEAR';
```

High-priority safety and out-of-scope events stay as event types because they alter the safety boundary and redirect strategy.

### Event Target

```ts
type EventTarget =
  | 'treatment'
  | 'recommendation'
  | 'documents'
  | 'consult'
  | 'pricing'
  | 'process'
  | 'travel'
  | 'payment'
  | 'hospital_selection'
  | 'medical_facts'
  | 'human'
  | 'unknown';
```

Notes:

- `timeline` is intentionally not included. Timing questions map to `process`.
- `contact` is intentionally not included as a follow-up target. Contact is information the user may provide, but the actionable follow-up is usually `human`.
- If contact appears in the event taxonomy during implementation, it should be limited to `USER_PROVIDED_INFORMATION` compatibility. It should not become a next-step invite target.

### Event Modifier

```ts
type EventModifier =
  | 'ask'
  | 'provide'
  | 'confirm'
  | 'reject'
  | 'hesitate'
  | 'revisit'
  | 'unknown';
```

Notes:

- `refine` is not included. Recommendation refinement such as "换一批", "更便宜的", or "上海的" maps to `modifier='revisit'`, with details carried in metadata or agent context later.
- `restart` is not included in Phase 1.1. Restart-like turns should be handled by target plus modifier or by explicit deterministic user actions in a later phase.

### Supervisor Event Shape

```ts
type SupervisorEvent = {
  eventType: DeterministicEventType | SemanticEventType;
  confidence: number;
  source: 'deterministic' | 'llm' | 'fallback_unknown';
  target?: EventTarget;
  modifier?: EventModifier;
  metadata?: SupervisorEventMetadata;
};
```

For LLM semantic extraction, the strict schema should require:

```ts
{
  eventType: SemanticEventType;
  target: EventTarget;
  modifier: EventModifier;
  confidence: number;
}
```

The adapter assigns `source='llm'`. The LLM must not output workflow state, stages, agents, write patches, tool calls, or old proposal fields.

## Mapping From Current Semantic Events

| Current event | New event shape |
|---|---|
| `USER_ASKED_NEXT_STEP` | `USER_ASKED_QUESTION`, `target=unknown`, `modifier=ask` |
| `USER_ASKED_FAQ` | `USER_ASKED_QUESTION`, target inferred as `pricing/process/documents/travel/payment/hospital_selection/unknown`, `modifier=ask` |
| `USER_WANTS_TREATMENT_IN_CHINA` | `USER_EXPRESSED_NEED`, `target=treatment`, `modifier=ask` |
| `USER_WANTS_DOCTOR_OR_HOSPITAL_MATCHING` | `USER_EXPRESSED_NEED`, `target=recommendation`, `modifier=ask` or `revisit` |
| `USER_PROVIDED_MEDICAL_FACTS` | `USER_PROVIDED_INFORMATION`, `target=medical_facts`, `modifier=provide` |
| `USER_INTERESTED_IN_CONSULT` | `USER_EXPRESSED_NEED`, `target=consult`, `modifier=ask` |
| `USER_REJECTED_OR_HESITATED` | `USER_RESPONDED_TO_REQUEST`, target inferred as `documents/human/pricing/unknown`, `modifier=reject` or `hesitate` |
| `USER_PROVIDED_CONTACT_INFO` | `USER_PROVIDED_INFORMATION`, `target=human`, `modifier=provide` |
| `USER_ASKED_RISKY_MEDICAL_ADVICE` | unchanged high-priority safety event |
| `USER_ASKED_OUT_OF_SCOPE_OR_RESTRICTED_SERVICE` | unchanged high-priority out-of-scope event |
| `USER_AMBIGUOUS_REPLY` | `USER_MESSAGE_UNCLEAR`, `target=unknown`, `modifier=unknown` |
| `UNKNOWN_MESSAGE` | `USER_MESSAGE_UNCLEAR`, `target=unknown`, `modifier=unknown`, `source=fallback_unknown` when applicable |

## TurnPlan

`TurnPlan` replaces the reducer's single action as the central control-plane output.

```ts
type TurnPlan = {
  primaryAction: PrimaryAction;
  followUpAction?: FollowUpAction;
  primaryStage: ChatJourneyStage;
  factsPatch: FactsPatch;
  reasonCode: string;
  sidePath?: SidePathInfo;
};
```

### PrimaryAction

```ts
type PrimaryAction =
  | { type: 'COLLECT_MINIMAL_TRIAGE' }
  | { type: 'GENERATE_RECOMMENDATION' }
  | { type: 'ASK_RECOMMENDATION_SELECTION' }
  | { type: 'SHOW_PROCESS_OVERVIEW' }
  | { type: 'REQUEST_MEDICAL_DOCUMENTS' }
  | { type: 'OFFER_ONLINE_CONSULT' }
  | { type: 'CREATE_HANDOFF' }
  | { type: 'ANSWER_QUESTION'; target: EventTarget }
  | { type: 'HANDLE_RESPONSE'; target: EventTarget; modifier: EventModifier }
  | { type: 'REDIRECT'; target: EventTarget; reason: 'out_of_scope' | 'safety' | 'unsupported' }
  | { type: 'CLARIFY'; target?: EventTarget; reason: 'ambiguous' | 'unknown' | 'missing_context' };
```

`REVISIT` is intentionally not a `PrimaryAction`. It is a modifier. The reducer interprets `target=recommendation, modifier=revisit` into a concrete recommendation action.

### FollowUpAction

```ts
type FollowUpAction =
  | {
      type: 'INVITE_NEXT_STEP';
      target:
        | 'minimal_triage'
        | 'recommendation'
        | 'documents'
        | 'consult'
        | 'process'
        | 'human'
        | 'unknown';
      reason?: string;
    }
  | {
      type: 'ASK_QUALIFYING_QUESTION';
      target: EventTarget;
      questionKey: string;
    }
  | { type: 'NONE' };
```

`ASK_CHOICE` is intentionally not included. A choice prompt is a type of qualifying question and can be expressed through `ASK_QUALIFYING_QUESTION` plus `questionKey`.

`RETURN_TO_MAIN_FLOW` is intentionally not included. It is too abstract and risks becoming a second reducer. Concrete next-step invites such as `documents`, `consult`, or `minimal_triage` express the intended main-flow return.

`INVITE_NEXT_STEP.target='contact'` is intentionally not included. Contact capture is already part of intake. If the user provides contact information later, the primary action should be `CREATE_HANDOFF` or the follow-up should invite `human`.

## Reducer Design

The reducer becomes:

```ts
function reduceJourney(event: SupervisorEvent, facts: DomainFacts, state: JourneyState): TurnPlan
```

Suggested handler structure:

```ts
switch (event.eventType) {
  case 'USER_EXPRESSED_NEED':
    return handleExpressedNeed(event, facts, state);
  case 'USER_ASKED_QUESTION':
    return handleQuestion(event, facts, state);
  case 'USER_PROVIDED_INFORMATION':
    return handleProvidedInformation(event, facts, state);
  case 'USER_RESPONDED_TO_REQUEST':
    return handleResponseToRequest(event, facts, state);
  case 'USER_REQUESTED_HUMAN':
    return createHandoffPlan(event, facts, state);
  case 'USER_ASKED_RISKY_MEDICAL_ADVICE':
    return safetyRedirectPlan(event, facts, state);
  case 'USER_ASKED_OUT_OF_SCOPE_OR_RESTRICTED_SERVICE':
    return outOfScopeRedirectPlan(event, facts, state);
  case 'USER_MESSAGE_UNCLEAR':
    return clarifyPlan(event, facts, state);
}
```

Example plans:

Pricing question during records collection:

```ts
{
  primaryAction: { type: 'ANSWER_QUESTION', target: 'pricing' },
  followUpAction: { type: 'INVITE_NEXT_STEP', target: 'documents', reason: 'pricing_requires_records' },
  primaryStage: 'COLLECT_MEDICAL_INPUTS',
  factsPatch: {},
  sidePath: { type: 'faq', primaryStagePreserved: true },
}
```

User refuses document upload:

```ts
{
  primaryAction: { type: 'HANDLE_RESPONSE', target: 'documents', modifier: 'reject' },
  followUpAction: { type: 'ASK_QUALIFYING_QUESTION', target: 'documents', questionKey: 'lower_friction_records_option' },
  primaryStage: currentStage,
  factsPatch: {},
  sidePath: { type: 'faq', primaryStagePreserved: true },
}
```

User provides contact information:

```ts
{
  primaryAction: { type: 'CREATE_HANDOFF' },
  followUpAction: { type: 'NONE' },
  primaryStage: 'HUMAN_HANDOFF',
  factsPatch: {},
}
```

## Authority And Projection

Authority remains reducer-owned:

- `primaryStage` is the single stage truth.
- `factsPatch` is the single write truth.
- Agents never decide stage or writes.
- Projection must mirror `TurnPlan.primaryStage` and `TurnPlan.primaryAction`.

`process.explained=true` should still only be written for `SHOW_PROCESS_OVERVIEW`, not for process FAQ answers.

Document upload behavior remains:

- Upload turn persists documents and stays with records handling.
- A later next-step turn can progress to consult if persisted facts show documents exist.

## Agent Roles

Phase 1.1 introduces conceptual roles while reusing current physical agents.

```ts
type AgentRole =
  | 'GeneralResponseAgent'
  | 'RecordsAgent'
  | 'RecommendationAgent'
  | 'ConsultHandoffAgent';
```

Initial mapping:

| Agent role | Current physical implementation |
|---|---|
| `GeneralResponseAgent` | `FaqAgent` |
| `RecordsAgent` | `RecordsAgent` |
| `RecommendationAgent` | `RecommendationAgent` |
| `ConsultHandoffAgent` | `ConsultAgent` or `HandoffAgent`, selected by primary action |

No physical agent rename is required for Phase 1.1.

### AgentResolver

Suggested mapping:

- Core records actions -> `RecordsAgent`
- Recommendation actions -> `RecommendationAgent`
- Consult invite/status -> `ConsultHandoffAgent`
- Handoff create -> `ConsultHandoffAgent`
- Answer, response handling, redirect, clarify -> `GeneralResponseAgent`

When a conceptual role maps to multiple physical agents, `primaryAction` chooses the concrete dispatch:

- `CREATE_HANDOFF` -> `HandoffAgent`
- `OFFER_ONLINE_CONSULT` -> `ConsultAgent`

## Skill Pack Registry

Phase 1.1 uses a code-defined registry.

```ts
type SkillPackId =
  | 'answer_then_advance'
  | 'ask_one_question'
  | 'clarify_ambiguous_reply'
  | 'service_scope_boundary'
  | 'medical_safety_boundary'
  | 'pricing_explanation'
  | 'cost_uncertainty_handling'
  | 'process_explanation'
  | 'travel_support'
  | 'payment_support'
  | 'objection_handling'
  | 'low_friction_next_step'
  | 'soft_redirect_to_main_flow'
  | 'minimal_triage_collection'
  | 'required_documents'
  | 'records_upload_conversion'
  | 'medical_records_summary'
  | 'doctor_matching_process'
  | 'hospital_recommendation'
  | 'recommendation_comparison'
  | 'revisit_previous_step'
  | 'online_consultation'
  | 'human_coordinator_handoff'
  | 'privacy_and_records_handling'
  | 'trust_building';
```

```ts
type SkillPack = {
  id: SkillPackId;
  title: string;
  summary: string;
  rules: string[];
};
```

Registry location should be code-owned and testable, for example:

```ts
apps/api/src/routes/chatbot-v3/skill-packs.ts
```

Phase 1.1 should not load skills from DB, CMS, or arbitrary markdown files.

## SkillRouter

```ts
type SkillPolicy = {
  allowedSkillPacks: SkillPackId[];
  maxSkillSnippets?: number;
};
```

No `forbiddenSkillPacks` in Phase 1.1. Safety and scope boundaries belong in `ResponseContract.safetyRules`.

SkillRouter is deterministic:

```ts
function buildSkillPolicy(input: {
  event: SupervisorEvent;
  turnPlan: TurnPlan;
  facts: DomainFactsSummary;
}): SkillPolicy
```

It combines skills from:

- `primaryAction`
- `followUpAction`
- `event.target`
- `event.modifier`

Examples:

| Signal | Skill packs |
|---|---|
| `ANSWER_QUESTION + pricing` | `pricing_explanation`, `cost_uncertainty_handling`, `answer_then_advance` |
| `INVITE_NEXT_STEP + documents` | `required_documents`, `records_upload_conversion` |
| `modifier=reject` | `objection_handling`, `low_friction_next_step` |
| `target=documents` | `required_documents`, `records_upload_conversion`, `medical_records_summary` |
| `target=consult` | `online_consultation`, `trust_building` |
| safety redirect | `medical_safety_boundary`, `ask_one_question` |
| out-of-scope redirect | `service_scope_boundary`, `soft_redirect_to_main_flow` |

Default `maxSkillSnippets` should be 6.

## AgentTask

TaskBuilder constructs the agent task from reducer truth, facts, retrieved context, and skills.

```ts
type AgentTask = {
  primaryAction: PrimaryAction;
  followUpAction?: FollowUpAction;
  latestUserMessage: string;
  conversationSummary: string;
  knownFacts: DomainFactsSummary;
  skillPolicy: SkillPolicy;
  retrievedContext?: {
    skillSnippets?: string[];
    knowledgeSnippets?: string[];
  };
  responseContract: ResponseContract;
};
```

```ts
type ResponseContract = {
  structure: 'answer_then_advance' | 'clarify_only' | 'system_notice';
  askOneQuestion: boolean;
  preservePrimaryStage: boolean;
  safetyRules: string[];
};
```

The agent receives enough context to write naturally, but not enough authority to change stage, facts, or dispatch.

## Data Flow

```text
User message
  -> SupervisorEventExtractor
     eventType + target + modifier + confidence
  -> JourneyReducer
     TurnPlan(primaryAction, followUpAction, primaryStage, factsPatch)
  -> AgentResolver
     conceptual agent role + physical dispatch agent
  -> SkillRouter
     allowedSkillPacks
  -> SkillRetriever
     3-6 code-defined snippets
  -> TaskBuilder
     AgentTask + ResponseContract
  -> Agent
     answer + follow-up text
  -> Composer
     final response/cards/debug
```

## Error Handling

Supervisor route failures:

- Invalid schema -> retry once -> `USER_MESSAGE_UNCLEAR`, `target=unknown`, `modifier=unknown`, `source=fallback_unknown`.
- Deterministic-only event from LLM -> reject.
- Unknown target/modifier -> sanitize to `unknown`.

Reducer fallback:

- Unhandled semantic combination -> `CLARIFY`, `primaryStage=currentStage`, `factsPatch={}`.
- Safety and out-of-scope preserve primary stage.
- `USER_REQUESTED_HUMAN` and direct contact handoff map to handoff creation, with `handoff.active` written only after runtime confirms creation.

Skill loading fallback:

- Missing skill id in registry -> omit it and emit observability warning.
- Empty skill set -> add `answer_then_advance` or `clarify_ambiguous_reply` based on action.
- Skill retrieval must not call LLM in Phase 1.1.

Agent fallback:

- General response policy fallback must produce safe bounded copy for safety, out-of-scope, and objection handling.
- Low-confidence FAQ/knowledge answers should not overwrite policy-grounded redirect text.

## Testing Strategy

### Layer 1: Supervisor Extraction

- Strict schema accepts only `eventType`, `target`, `modifier`, `confidence`.
- Deterministic events are not allowed from semantic LLM.
- All current semantic guide cases map into the generic taxonomy.
- Invalid target/modifier sanitizes to `unknown`.
- Old proposal fields still fail.
- Metadata remains disallowed unless explicitly reintroduced.

### Layer 2: Reducer / TurnPlan

Cover:

- `USER_EXPRESSED_NEED + treatment + ask`
- `USER_EXPRESSED_NEED + recommendation + ask`
- `USER_EXPRESSED_NEED + recommendation + revisit`
- `USER_ASKED_QUESTION + pricing/process/documents/payment/travel`
- `USER_PROVIDED_INFORMATION + medical_facts`
- `USER_PROVIDED_INFORMATION + human + provide`
- `USER_RESPONDED_TO_REQUEST + documents + reject`
- `USER_RESPONDED_TO_REQUEST + unknown + hesitate`
- safety redirect
- out-of-scope redirect
- unclear message
- deterministic submit/select/upload paths

Every reducer test should assert:

- `primaryAction`
- `followUpAction`
- `primaryStage`
- `factsPatch`
- side-path preservation
- reason code

### Layer 3: AgentResolver / SkillRouter / TaskBuilder

Assert:

- General response actions map to conceptual `GeneralResponseAgent` and physical `FaqAgent`.
- Core workflow actions map to Records, Recommendation, Consult/Handoff as expected.
- Pricing question plus document follow-up loads pricing and required-document skills.
- Reject/hesitate loads objection handling and low-friction next step skills.
- Safety loads medical safety boundary.
- Out-of-scope loads service scope boundary.
- ResponseContract preserves primary stage for side paths.

### Layer 4: Runtime Session Tests

Run multi-turn sessions:

1. Happy path from treatment need to triage, recommendation, process, documents, consult.
2. Pricing question during document collection answers then invites documents.
3. Process question from online consult does not rewind to explain process.
4. Document upload two-turn behavior remains unchanged.
5. Recommendation revisit asks or regenerates recommendation without inventing a new event type.
6. Document refusal answers softly and preserves stage.
7. Direct contact information creates handoff.
8. Risky medical request uses safety boundary and preserves stage.
9. Out-of-scope request redirects to Medora-supported workflow and preserves stage.
10. Invalid schema fallback clarifies and recovers next turn.

## Migration Plan

Phase 1.1 should be implemented in clear slices:

1. Add generic event types, target, and modifier to shared application types.
2. Update semantic prompt and route adapter schema.
3. Replace semantic event-specific reducer branches with generic handlers.
4. Introduce `TurnPlan` while keeping a temporary compatibility projection to legacy `nextAction` where needed.
5. Add AgentRole and resolver mapping while preserving physical agents.
6. Add code-defined skill pack registry.
7. Add SkillRouter and TaskBuilder fields.
8. Update runtime/composer to support answer-then-advance.
9. Rewrite tests from old semantic event names to generic taxonomy.
10. Remove old semantic event names from prompt guide and allowed semantic events after tests pass.

## Open Questions

1. Should direct contact information use `target=human` or reintroduce `target=contact` only for event classification?
   - Current design prefers `target=human` to avoid follow-up contact capture ambiguity.
2. Should recommendation revisit immediately regenerate recommendations or first ask a qualifying question?
   - Current design leaves this to reducer policy and facts.
3. Should `INVITE_NEXT_STEP(target=process)` ever write `process.explained=true`?
   - Current answer: no. Only `SHOW_PROCESS_OVERVIEW` writes `process.explained=true`.
