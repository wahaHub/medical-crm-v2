# Shared Patient Phase 2 Backend Contracts Design

## Goal

Define the shared CRM v2 backend/contracts for the next patient-portal phase used by both:

- Medora Health Beauty
- China Medical Journeys

This phase expands beyond Phase 1 (`ChatWidget -> onboarding -> hospital selection -> messages`) and standardizes the next layer of shared patient-facing backend capability:

- tickets
- orders
- journey
- AI summary
- patient-facing package purchase contracts

This spec also includes the required admin, hospital, and internal contract adjustments needed to support the patient experience cleanly.

## Why This Spec Exists

The existing backend already contains substantial domain and admin/hospital use case coverage for tickets, orders, and journey. What is missing is a clean shared patient contract that:

- both websites can consume without frontend-specific coupling
- keeps patient APIs separate from admin/hospital operational APIs
- leaves a safe internal entry point for future AI chatbot ticket creation
- keeps payment expansion possible without redesigning order contracts later

This is a new shared phase. It is not derived from or constrained by unrelated earlier phase-2 documents.

## Product Outcomes

By the end of this phase, the shared backend/contracts must support all of the following:

- patient can create, list, view, and reply to support tickets
- admin can continue managing and replying to tickets
- future AI chatbot can create tickets through an internal trusted route
- patient can browse purchasable packages and create an order from a package
- patient can view their own orders and initialize payment for an order
- patient can read case-level journey information and visible milestones
- admin remains the only actor who can update journey
- patient can read case-level AI summaries

## Scope

### In Scope

- new patient-facing `/api/patient/*` contracts for:
  - tickets
  - orders
  - journey
  - AI summary
  - packages
- internal AI ticket-creation contract
- required admin/hospital/internal contract changes to support patient phase 2
- ownership, visibility, status, and validation rules
- payment-ready order contract design
- test and verification requirements for the shared backend

### Out of Scope

- frontend implementation details for China or Medora
- payment provider integration details
- AI summary generation pipeline redesign
- AI chatbot UX
- package CMS redesign
- intake contract redesign
- hospital-side journey editing expansion

## Architecture Direction

This phase uses two layers:

1. `resource contracts`
2. `portal aggregates`

### Resource Contracts

These are the long-lived backend resources with clear ownership and stable semantics:

- `packages`
- `orders`
- `tickets`
- `journey`
- `ai summaries`

These contracts must remain frontend-agnostic and reusable across both websites.

### Portal Aggregates

These are lightweight read models built for portal screens when a direct resource read is too fragmented.

This spec does not require a large new aggregate-first architecture. Aggregates should stay thin and only be added when they simplify real portal screens without weakening the underlying resource contracts.

The default rule is:

- design resource contracts first
- add aggregates only when a patient portal screen clearly needs them

## Domain Model

### Ticket

`ticket` is a patient-level object.

Properties:

- belongs to `patientId`
- may link to `caseId`
- does not require `caseId`
- can contain replies
- can be created by patient or internal AI flow

Key design rule:

- tickets are not scoped under a case route, even when linked to a case

### Order

`order` is a patient-level object.

Properties:

- belongs to `patientId`
- may link to `caseId`
- does not require `caseId`
- must originate from `packageId`
- is the future anchor for payment

Key design rule:

- patient cannot create a free-form order
- patient can only create an order from a package

### Journey

`journey` is a case-level object.

Properties:

- exactly tied to a `caseId`
- patient can read
- admin can update
- milestones remain separate but related case-level resources

Key design rule:

- patient reads a filtered journey view, not the admin editing model directly

### AI Summary

`ai summary` is a case-level object.

Properties:

- tied to a `caseId`
- generated by AI/system workflows
- patient reads only
- admin and hospital may read through their own surfaces

Key design rule:

- AI summary is per case, not global per patient

### Package

`package` is the catalog object from which patient orders originate.

This phase does not redesign package authoring, but it must define a stable patient-facing purchasable package contract.

## Permission Matrix

### Tickets

- `patient`
  - create
  - list own
  - get own
  - reply own
- `admin`
  - create
  - list
  - get
  - assign
  - reply
  - update status
  - close
- `hospital`
  - no new direct ticket-management surface in this phase
- `internal AI`
  - create only, through internal trusted route

Notes:

- admin reply already exists and remains supported
- patient reply to a `PENDING_INFO` ticket should continue transitioning the ticket back to `ASSIGNED`

### Orders

- `patient`
  - list own
  - get own
  - create from package
  - create payment intent for own order
- `admin`
  - list
  - get
  - update status
  - create payment intent when needed for admin-operated flows
  - request/process refund according to existing order flows
- `hospital`
  - no new order write surface in this phase
- `internal AI`
  - cannot create orders

### Journey

- `patient`
  - read journey
  - read patient-visible milestones
- `admin`
  - read
  - update journey
  - create milestone
  - update milestone
  - delete milestone
- `hospital`
  - no new write permissions in this phase

Notes:

- current codebase already enforces admin-only journey updates, and this spec preserves that rule

### AI Summary

- `patient`
  - read case-level summary
- `admin`
  - read
- `hospital`
  - read through their own surfaces
- `AI/system`
  - generate or refresh through internal workflows, not patient routes

### Packages

- `patient`
  - list purchasable packages
  - read package detail
- `admin`
  - manage packages through existing/admin contracts
- `hospital`
  - no new package-management requirements in this phase

## Ticket Types

This phase standardizes the patient-facing ticket types as:

- `GENERAL_SUPPORT`
- `MEDICAL_QUESTION`
- `QUOTE_PRICING`
- `PACKAGE_ORDER`
- `PAYMENT_REFUND`
- `TRAVEL_JOURNEY`
- `ACCOUNT_TECHNICAL`

Design notes:

- this enum is shared across patient creation, admin processing, and future AI chatbot mapping
- if AI classification is uncertain, it should default to `GENERAL_SUPPORT`
- urgency is not modeled as `type`; it remains a separate concern such as `priority`

## Contract Design

### Patient-Facing Routes

Patient-facing routes live under `/api/patient/*`.

### Tickets

- `POST /api/patient/tickets`
- `GET /api/patient/tickets`
- `GET /api/patient/tickets/:id`
- `POST /api/patient/tickets/:id/replies`

`POST /api/patient/tickets`

Input:

- `type`
- `description`
- optional `subject`
- optional `caseId`
- optional `priority`
- optional `sourcePage`

Rules:

- `caseId` is optional but, if supplied, must belong to the authenticated patient
- patient cannot set admin-only fields such as `assignedTo`, `status`, or internal notes

`GET /api/patient/tickets`

Returns only tickets owned by the authenticated patient.

Should support pagination and lightweight filtering by:

- `status`
- `type`

`GET /api/patient/tickets/:id`

Returns:

- ticket detail
- visible replies only

Patient must not see internal notes.

`POST /api/patient/tickets/:id/replies`

Input:

- `content`
- optional `attachments`

Rules:

- patient can only reply to own tickets
- patient cannot mark `isInternalNote`

### Orders

- `GET /api/patient/orders`
- `GET /api/patient/orders/:id`
- `POST /api/patient/orders`
- `POST /api/patient/orders/:id/payment-intents`

`POST /api/patient/orders`

Input:

- `packageId`
- optional `caseId`

Rules:

- package must be purchasable
- if `caseId` is supplied, it must belong to the authenticated patient
- patient cannot submit raw amount, currency, or status
- order pricing must be derived from the package contract, not trusted from client input

Output:

- created `order`
- enough payment state to continue to payment-init flow without extra guessing

`POST /api/patient/orders/:id/payment-intents`

Rules:

- patient can only create payment intent for own order
- order must be in a payment-eligible state
- response must be designed to plug into later payment integration without changing the route shape

### Journey

- `GET /api/patient/cases/:caseId/journey`
- `GET /api/patient/cases/:caseId/milestones`

Rules:

- patient can only read own case journey
- milestones must respect `isVisibleToPatient`
- patient route must not expose admin-only editing semantics unnecessarily

### AI Summary

- `GET /api/patient/cases/:caseId/ai-summary`

Output should return a structured shape with at least:

- `status`
- `summary`
- optional metadata such as `language` or `updatedAt`

Rules:

- missing summary is a valid empty state, not an error
- if generation is pending, return explicit status instead of forcing frontend inference

### Packages

- `GET /api/patient/packages`
- `GET /api/patient/packages/:id`

These routes define the patient purchasable view, not the full admin package shape.

The patient-facing package contract should include only what is needed for:

- package browsing
- package comparison
- package detail display
- order creation

## Internal AI Contract

Future AI chatbot ticket creation should use a separate trusted route, for example:

- `POST /api/internal/ai/tickets`

Rules:

- this route is not patient-authenticated
- it must use explicit internal trust/auth controls
- it should call the same core create-ticket use case used by patient/admin entry points
- it must support source attribution for auditability

Required internal metadata:

- `source = AI_CHATBOT`
- patient identity or resolvable patient context
- optional linked `caseId`
- chosen or fallback `ticketType`
- original AI context payload if audit logging requires it

This route exists to keep business logic shared while keeping the public patient contract locked down.

## Admin And Hospital Contract Adjustments

This phase does not redesign admin/hospital APIs wholesale, but it explicitly allows contract adjustments when required to support patient phase 2.

Examples:

- ensure package contracts expose enough purchasable data for patient ordering
- ensure order contracts preserve payment-related metadata needed for later payment work
- ensure journey and milestone read paths cleanly support patient-visible filtering
- ensure ticket contracts support source attribution for AI-created tickets

Guiding rule:

- adjust admin/hospital/internal contracts only when necessary to make the shared patient contract correct and stable

## Read Model Principles

### Patient Journey Read Model

Patient journey reads should be shaped for consumption, not for admin editing.

That means:

- patient sees only relevant fields
- patient sees only visible milestones
- admin-only operational fields should stay outside patient routes

### Patient AI Summary Read Model

Patient AI summary should be a dedicated case-level read model.

Do not hide AI summary only inside a large case aggregate. It needs its own stable contract because:

- both portals need it
- frontend loading states differ
- generation status matters

### Portal Aggregates

If a future portal aggregate is needed, it should consume these stable resource contracts instead of replacing them.

Examples that may be acceptable later:

- patient dashboard summary
- case overview aggregate

But this spec does not require a large new aggregate-first API.

## State Semantics

### Ticket Status

The shared ticket status model remains:

- `OPEN`
- `ASSIGNED`
- `IN_PROGRESS`
- `PENDING_INFO`
- `RESOLVED`
- `CLOSED`

Patient-facing semantics:

- patient can read all statuses
- patient does not directly change status
- patient reply to `PENDING_INFO` transitions back to `ASSIGNED`

### Order Status

The patient-facing order contract should support at least:

- `PENDING_PAYMENT`
- `PAID`
- `IN_PROGRESS`
- `COMPLETED`
- `REFUNDED`
- `CANCELLED`

Patient-facing semantics:

- patient-created orders should normally begin at `PENDING_PAYMENT`
- patient cannot directly mutate status
- payment-intent creation must be limited to eligible states

### AI Summary Status

AI summary should return explicit state rather than only nullable content.

Minimum states:

- `EMPTY`
- `PENDING`
- `READY`
- `FAILED`

This keeps frontend behavior deterministic on both websites.

## Error Handling

Shared backend contracts should use stable, predictable failure semantics.

Recommended response classes:

- `400` for invalid input
- `401` for unauthenticated calls
- `403` for ownership/permission failures
- `404` for missing resources
- `409` for valid-but-disallowed state conflicts

Examples of `409`:

- package is not purchasable
- order is not payment-eligible
- linked case does not belong to the correct patient state for the requested action

Key requirement:

- responses must make it clear whether the problem is bad input, bad ownership, or bad resource state

## Testing Requirements

This phase should be verified primarily at the application and API-contract layers.

Required coverage areas:

- patient ticket create/list/get/reply ownership
- patient ticket replies excluding internal notes
- AI internal ticket creation auth and source attribution
- patient order creation from package only
- rejection of free-form patient order creation
- patient order ownership checks
- payment-intent eligibility checks
- patient journey visibility filtering
- patient AI summary empty/pending/ready behavior
- optional `caseId` validation for ticket and order creation

At minimum, this phase should include:

- application use case tests
- API route tests
- auth/ownership tests

This phase does not require deep payment-provider integration tests yet.

## Rollout Guidance

Implementation should proceed in this order:

1. stabilize shared application contracts and DTO shapes
2. expose patient routes
3. add internal AI ticket-creation route
4. patch admin/hospital/internal contract gaps required by patient routes
5. let China frontend and Medora frontend integrate afterward

This order keeps the shared backend authoritative and avoids frontend-specific drift.

## Acceptance Criteria

This spec is satisfied when:

- patient tickets work end to end without requiring case-scoped routes
- patient orders can only be created from packages
- order/payment contract shape is stable enough for later payment integration
- patient can read journey and visible milestones
- patient can read case-level AI summary through a dedicated contract
- AI chatbot has a separate trusted ticket-creation entry point
- shared contracts are reusable by both websites without frontend-specific branching
